# Evolution of the Saum idea

**Status:** historical interpretation of the supplied discussion, not a sequence of formally adopted decisions. The order below follows the conceptual progression; only dates explicit in source documents should be treated as source timestamps.

## 1. Starting point: a deterministic outer manager for Ralph

The original inventory assumes a mature specification/backlog and bounded workers materializing it. It separates a permanent graph of settled artifacts from an execution DAG containing experiments, monitors, reviews, human gates and synthesis.

The application owns legal transitions and information boundaries; agents operate inside nodes. Extensive interaction ideas include model choice, budgets, experiment duplication, code annotations, selective reuse and graph editing.

**What remains:** accepted state, provenance, bounded authority and the two-graph distinction. **What changed:** it is no longer assumed that the core must own every local execution step.

## 2. Competitive critique narrows the claim

The early comparison challenged novelty in multi-agent execution, DAG engines, issue-to-PR automation and generic specification workflows. It proposed that the more interesting claim is versioned engineering authority, evidence-driven acceptance and incremental reconciliation.

The comparisons themselves contain product-specific claims that were not verified for this dossier. The durable implication is a burden of proof, not a settled market conclusion: demonstrate value beyond an assembly of existing tools.

**Open:** whether the integrated model is sufficiently useful to justify a separate system rather than a thin layer.

## 3. V5 provides evidence but not a complete proof

The supplied review rejects four ready claims, preserves useful partial results and observes that the manager-owned frontier held. It also exposes a public success claim on an unfinished branch.

Earlier v4 manager work is reported as already surfacing credential/authentication ambiguity. That is some evidence of the mechanism's usefulness, but the v5 review explicitly cannot claim blind discovery because hypotheses and previous assessments were visible.

**What remains:** worker progress is evidence, not authority; failed branches can teach. **Not established:** reliable generic manager prompting, guidance improving a held-out cohort, accepted foundation, long-horizon economics or successful cross-project reconciliation.

## 4. The user separates costly prototype behavior from the intended policy

The user argues that Scenario 01 is broad and that an eventual coordinator should identify consequential uncertainties before paying to rediscover everything. Some questions merit discussion, some focused experiments, and some ordinary implementation.

At the same time, open-ended first-milestone work is valuable because it pressures the upstream specification. Preselecting obvious fixture mechanisms can hide ambiguity.

**Refinement:** aim for targeted uncertainty reduction without eliminating the discovery surface. The v5 whole-milestone fan-out is not itself the final exploration policy.

## 5. Stable worker protocol versus temporary guidance

The assistant's warning against endlessly hardening Ralph could be read as avoiding feedback. The user clarifies that Saum should absolutely be able to tilt the next attempt using milestone-specific opinions and learnings.

**Refinement:** stable protocol, durable project decisions, temporary guidance and one-off rejected mistakes have different destinations. Temporary guidance must not silently change upstream authority.

## 6. The tool ladder exposes a more generic model

The user contrasts IC-like local tasks, higher-level issue/PR delegation, role-based workflows and specification flows with the desired ability to govern product/architecture and then review different downstream projects.

The user then generalizes the artifact hierarchy to a school strategy, annual plan and grade plans. An agent's role follows from its artifact responsibility; named software roles are not essential.

**Working direction:** a generic reconciliation layer above heterogeneous project methods, with software as the immediate proving ground.

## 7. "Projects are black boxes" proves too weak

Narrowing the core initially suggests simply requesting a new revision and receiving findings/evidence. The user identifies the loss: the project may solve or discard a strange path without recognizing its upstream significance.

**Refinement:** projects are encapsulated but observable. The interface must expose candidate state and adequate evidence; it cannot rely only on polished local summaries or declarations of success.

## 8. Requiring perfect project self-diagnosis also proves too weak

An early response proposes a required set of upstream findings from every project. The user objects that this is hard to enforce with complex procedural prompts and can lose precisely the evidence the outer reviewer needs.

**Refinement:** local observations and direct blockers are useful but not the exclusive information channel. Preserve provenance and let cross-project review interpret it, with depth chosen according to value and cost.

**Open:** how to capture and index enough evidence without making every run expensive or requiring a mega-agent to read everything.

## 9. Experiment ownership moves out, then partly back

One direction puts experiments entirely inside projects as a reusable capability. The user then proposes generic project-level branching: each isolated instance performs an ordinary request while Saum compares the results.

This can avoid duplicating the same alternatives/review infrastructure inside every method, including a school workshop. Yet it adds workflow scope to a system otherwise focused on artifact relationships.

**Current position:** the generic multi-candidate operation is promising. Core versus optional service versus project-local method remains unsettled. Whole-subtree fan-out remains exploratory.

## 10. Global/local impact analysis is corrected by the real project shape

Early examples made Foo, Timeline, Export and API separate projects, making decomposition look easy. The user corrects this: one Implementation project may contain all of them, with Design and Harness as its two upstream projects.

**Refinement:** Saum needs a negotiation boundary for large batches suited to the project's local reality. The project knows both its domain and its method; the coordinator knows global relationships and intent. Neither simply dictates every local task.

## 11. Tight adapters are challenged

Listing specific framework adapters implied deeper integration than the user's preferred standalone-repository model. The useful contract may be ordinary requests and artifact/evidence returns, not access to the framework's complete internals.

**Current position:** adapters are optional implementation aids. The architectural requirement is a usable reconciliation/validation boundary, not a custom integration with every vendor.

## 12. Milestones are reinterpreted rather than simply removed

The original model used sequential backlog frontiers. Later discussion proposed work packages or reconciliation units because independent changes can run concurrently or be regrouped.

The validation branch adds meaningful settlement increments and living plans. A milestone can remain a review boundary without prescribing all internal tasks or forcing linear execution.

**Current interpretation:** preserve scope and acceptance boundaries, but do not equate them with a fixed sequential task list. Exact vocabulary and representation remain open.

## 13. Human review does not automatically imply a new project

The user wonders whether needing internal human settlement means an intermediate Design project should exist. The discussion distinguishes internal workflow decisions from independently authoritative state.

**Working criterion:** create a node when the knowledge deserves independent revision, governance or consumers, not for every approval step. Internal human review remains valid inside a project.

## 14. Allium adds a constrained materialization surface

The user proposes Allium either as the root or as a behavioral projection below arc42. The later preference is arc42 at the top, with a Behaviour Model useful to Harness, Design and Implementation.

**What it adds:** a potentially cheaper way to expose behavioral gaps before full implementation. **What it does not settle:** exact tool capabilities, complete coverage, faithfulness of the prose-to-model interpretation, or direct dependency edges for every consumer.

The risk of shared interpretation is preserved: if every downstream project obeys one unreviewed model, agreement can hide the source ambiguity.

## 15. Access and conformance dependencies are separated, provisionally

The user wants all projects to understand the architecture's why and the model's behavior. The assistant proposes context relationships distinct from hard readiness/dependency edges.

**Useful distinction:** visibility is not automatically authority. **Unresolved tension:** if the supposedly contextual artifact contains applicable obligations, how are they carried into conformance and invalidation? The final diagram in the main thread should not be treated as a settled universal topology.

## 16. Validation branch: authority need not mean executing every check

The branch begins with the concern that Saum must understand arbitrary outputs to settle them. It proposes separating candidate production, independent conformance evaluation and the acceptance decision.

It further distinguishes reconciliation, artifact and validation contracts, with validation potentially associated with dependency edges.

**Refinement:** Saum governs the acceptance process, but specialized tools, agents and humans can execute validation. Settlement is evidence-backed acceptance under policy, not a guarantee of correctness.

## 17. Validation branch: living plans and conservative partial acceptance

The user's proposal is to preserve negotiated increments and recalibrate them after learning from accepted progress. Objective, plan and settlement criteria remain separate; the planning horizon can be shorter than the full obligation.

The branch distinguishes accepted internal checkpoints from global settlement and favors full upstream reconciliation before downstream use in an initial version. New increments need regression checks and final integrated validation.

**Status:** a strong candidate model, not an agreed mandatory release policy for all future versions. Partial scoped consumption, claims representation and replanning triggers remain open.

## 18. Reconstruction branch: reverse evidence, not authority

The legacy example starts from Cosmos code and climbs upward into candidate Design, behavior and Architecture. The branch proposes preserving the normative graph rather than reversing it.

Characterization records current behavior. Human intent helps decide what becomes required. The pivot creates accepted upstream authority, after which existing code may immediately need reconciliation.

**What this reinforces:** artifacts generated from evidence do not automatically become truth. Reconstruction is an onboarding posture, not permission to canonize every legacy behavior.

## 19. What has not been reconciled into one final architecture

The discussions have not selected a complete runtime, storage model, edge schema, state machine, framework integration strategy, validation formalism, partial-release policy or scope for experimental orchestration.

This dossier intentionally preserves those forks. A future Architecture project should resolve them explicitly with the human, rather than treating chronological recency or polished branch prose as sufficient authority.
